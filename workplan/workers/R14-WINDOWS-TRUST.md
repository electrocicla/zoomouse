## Cascading threat/authority analysis (before any source change)
1. Android untrusted QR/IP and JS bridge provide **no** native authority; Kotlin secure-LAN module is deny-only. No Android→Windows encrypted control session or verified DTLS exporter, both certificate fingerprints and SCTP stream/generation exist in production.
2. Host `channel_binding`/admission provide source-only verification state machines, not a native DTLS/SCTP producer or physical OS approval callback; no device/session-bound native grant can be constructed by this Windows shell.
3. Tauri `host_status` and `emergency_stop` are read/deny IPC only. Tauri tray show/revoke/quit are local UI actions but **not consent**; `DisabledInput` is the sole backend, no permission factory. `desktop_observer` checks console session and exact input desktop read-only; positive observation cannot approve.
4. Private `crates/control/src/native.rs` requires matching console, thread/input desktop, exact terminated UOI_NAME, successful CloseDesktop on every SendInput. R13 already fixed lock/poison/cleanup retry; do not duplicate.
5. **Concrete remaining negative path:** Unicode `Action::Text` sends a paired key-down/key-up via SendInput. Partial native SendInput (key-down accepted, key-up not accepted) followed by failed best-effort key-up can leave an injected Unicode key held, while `Executor` owns no `Key` for this transient UTF-16 code unit. Its generic `release(keys,buttons)` may return success with empty held sets, incorrectly clearing `cleanup_failed`. All remote input remains blocked, but this is a real future native resource-leak risk.

Terminal/revoke/drop must attempt pending Unicode ups together with held key/button ups; return failure if any remain. No desktop bypass, injected positive test, API surface or new deps.
